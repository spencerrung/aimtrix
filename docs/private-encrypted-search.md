# Private encrypted-history search

Issue [#158](https://github.com/spencerrung/aimtrix/issues/158) adds an opt-in, device-local index for joined encrypted rooms. Server search remains restricted to unencrypted rooms. Indexing never sends decrypted message text, derived keys, passphrases, or index queries to Matrix account data or a separate search service. Message context still opens through the controller's exact-event route, which can report a removed or inaccessible event.

## Threat and storage model

Each normalized Matrix user ID and homeserver URL owns a separate IndexedDB database, independent of drafts and SDK crypto stores. The database name, room/event IDs, timestamps, cursors, counts and skipped-event totals are local plaintext metadata. Sender IDs, message type and up to 2,000 characters of body text per event are AES-256-GCM ciphertext with the account and event key as associated data. A random 16-byte salt and encrypted verifier accompany the database. The user supplies a local passphrase of at least 12 characters; PBKDF2-SHA-256 with 310,000 iterations derives a non-extractable session key. The passphrase and key are never persisted. A restart requires the passphrase again. A forgotten passphrase requires deleting and rebuilding the index.

This protects index text against casual inspection of browser storage without the passphrase. It does **not** protect against malicious same-origin JavaScript while the index is unlocked, a compromised device/browser profile, a weak passphrase, or the Matrix server seeing room/event metadata. Browser draft storage has a separate plaintext contract in [draft storage](draft-storage.md); drafts are not indexed. Clearing browser site data removes both stores. No released private-search format exists to migrate. The local schema upgrade from IndexedDB version 1 to 2 adds edit tombstones without copying plaintext. Future unknown versions are rejected rather than overwritten; damaged ciphertext entries are skipped and shown in the search panel.

## Coverage and lifecycle

Indexing begins only after the user unlocks the local index and chooses a joined encrypted room. It first scans the loaded live timeline, then uses independent Matrix `/rooms/{roomId}/messages` backward pages. One action requests at most 20 pages of 50 events and yields between pages so sync and composition can run. The index caps at 5,000 distinct events per account and never silently evicts an existing result. The panel shows count, oldest/newest indexed message dates, missing-key skips, whether the available history was exhausted, cancellation, and explicit deletion. A cancelled run keeps already committed pages and its continuation cursor; the SDK's in-flight `/messages` request has no AbortSignal, so cancellation takes effect after that request completes. Search decrypts bounded local records in chunks, applies sender/date/type filters, and pages displayed local results in groups of 30. These ranges describe indexed events, not a guarantee that every message in the room is searchable. Missing keys can leave gaps; after recovering keys, delete and rebuild the index to revisit skipped pages.

Redactions remove indexed events even if the passphrase is locked. Edits are accepted only when the original encrypted event has the same sender; they remove old indexed words and record a metadata tombstone so an older page cannot restore stale text. When unlocked, the replacement body can be indexed under the original event ID. Losing room membership blocks new writes and removes its indexed events and cursor. Final IndexedDB write transactions recheck those tombstones and room blocks across tabs. Results are also filtered against current joined-room state before display. Explicit logout or forgetting a session closes the index and deletes its account database along with SDK account databases; temporary authentication recovery closes the in-memory key but retains the database for the same account. Browser denial, blocked deletion by another tab, and quota failures are surfaced without interrupting ordinary messaging. Optional index deletion failure does not prevent credential clearing, but the signed-out screen reports the residual local data and instructs the user to clear site data. Concurrent tabs can operate on the same index but simultaneous backfill is not coordinated; duplicate event keys are deduplicated.

## Evidence remaining

Unit tests cover at-rest ciphertext, restart/passphrase behavior, account isolation, filters, damaged records, locked redaction and room cleanup, edit tombstones, version refusal, storage denial and controller backfill. Desktop/mobile Chromium tests cover unlock, index, restart, search, deletion and accessibility. A synthetic Node 22/fake-indexeddb measurement of 20 pages × 50 messages took 294 ms to index and 179 ms to search all 1,000 records after a 197 ms passphrase unlock; observed heap growth was about 5 MiB. That is a local algorithm baseline, not a browser or network benchmark, and the 5,000-record cap bounds storage and scans. The [disposable live harness](live-matrix-tests.md) now exercises older-history indexing on a device with keys and on Charlie's first browser device, which joined the room before the messages but had no earlier room-key session. It checks indexed date coverage, missing-key gaps, local search and exact context, encrypted sending after a gap, deletion, and absence of the synthetic history text or local passphrase in outbound browser request bodies. Hosted Synapse results are still required before this live acceptance can close; native storage-provider behavior remains a separate release boundary in [#175](https://github.com/spencerrung/aimtrix/issues/175). The request-body check observes these disposable journeys, not every possible browser extension, script, or future code path.
