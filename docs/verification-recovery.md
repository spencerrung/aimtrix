# Fresh-device verification recovery

A device that has just signed in can request verification before Aimtrix has received its signed device keys. With Matrix JS SDK 42.2.0 and Rust crypto WASM 18.5.0, that request can be discarded inside crypto processing. Downloading the keys afterward does not restore the original transaction. The same memory-only proof also reproduces this behavior in Rust 18.9.0, the dependency required by JS SDK 44.0.0. Updating that dependency alone is not an established remedy.

Aimtrix handles this boundary with explicit recovery for self-account to-device requests ([#291](https://github.com/spencerrung/aimtrix/issues/291), related to [#161](https://github.com/spencerrung/aimtrix/issues/161)). A failed-attempt notice explains that verification did not start. The notice checks whether the named device is present in the SDK's own device map. While keys are unavailable, it asks the user to wait for sync and check again; a failed check has separate connection guidance. Once the keys are available, the user must cancel the pending attempt on the other device and request verification again there. The new request must pass the ordinary SDK verification flow, including emoji or QR confirmation. The recovery notice never marks a device trusted.

“Check device again” reads the SDK device state through `CryptoApi.getUserDeviceInfo`. For the tracked own user this waits briefly for an existing key query; it does not force a download. `CryptoEvent.DevicesUpdated` also refreshes the notice. “Dismiss notice” only hides local guidance and explicitly does not cancel the peer's request. Restoring an existing recovery key in Settings remains another way to recover the account.

## Protocol and lifecycle contract

The implementation observes the supported `ClientEvent.ReceivedToDeviceMessage` event, after the SDK has processed the message. It compares the original sender and transaction against SDK-owned requests; it neither replays raw events nor calls private crypto methods. The public `CryptoApi` has no request-replay hook. Production behavior is separate from any test-only known-device barrier.

Only requests from the signed-in user's account are eligible. The claimed device must differ from the current device; sender, device and transaction are validated before use, as are supported methods and Matrix timestamp bounds. For encrypted events, the decrypted sender/device metadata must agree with the request. A notice labels the device as named by the request, not authenticated by it. Availability requires matching user/device fields from the SDK map. No raw message contents, keys, transaction IDs or errors are logged or persisted, and no cancellation is sent using an unauthenticated `from_device` value.

At most five notices and 128 transaction deduplication entries are retained in memory. Notices expire after two minutes or the request's ten-minute timestamp window, whichever is earlier; deduplication expires after ten minutes. Cancel/done events, a matching SDK request, or a newer SDK request for the same device remove the notice. Other devices remain independent. Pending lookups cannot recreate dismissed, cancelled, superseded or expired notices. Account teardown detaches every listener, clears timers and notices, and ignores late results.

## Verification and limits

- `node tests/live-matrix/verification-request-loss.mjs` runs actual memory-only Rust crypto: an unknown-device request is absent, stays absent after a signed key query, and a distinct known-device request exists. It emits only three booleans or a fixed failure category.
- `npx vitest run src/matrix/VerificationRecovery.test.ts src/matrix/MatrixController.incomingVerification.test.ts src/features/workspace/IncomingVerification.test.tsx` covers recovery, validation, expiry, cancellation, supersession, account cleanup and ordinary SAS/QR phases.
- `npm run test:e2e -- e2e/verification-recovery.spec.ts` checks the recovery UI, keyboard controls, mobile bounds and Axe, using synthetic fixture data. It does not establish protocol interoperability.
- After `npm run build`, `flock -x /tmp/aimtrix-audit-network.lock node tests/live-matrix/verification-recovery.mjs` starts isolated disposable Synapse and Element containers. It holds receiver key queries across a real Element fresh login, requires failed-attempt guidance and no verification controls, releases signed keys, requires explicit peer cancellation and a distinct new transaction, then compares all seven emoji and completes verification on both clients. Set `AIMTRIX_VERIFICATION_OUTPUT` for the allowlisted JSON report; no browser traces, session exports, raw errors or screenshots are saved. Coordinate this exclusive Docker gate with other local browser work.

Transparent preservation of the original dropped transaction remains an upstream SDK boundary. This recovery does not claim to solve cross-user unknown-device requests, reverse QR interoperability, physical-camera acceptance or the broader remaining work in #161.
