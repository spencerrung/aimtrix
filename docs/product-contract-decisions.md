# Product contracts: expression, scheduling, and integrations

These are decisions for [#170](https://github.com/spencerrung/aimtrix/issues/170), [#172](https://github.com/spencerrung/aimtrix/issues/172), and [#173](https://github.com/spencerrung/aimtrix/issues/173). They do not enable a new control or publish any user data. The static, backend-free default remains the release contract.

## Profile expression — defer public decoration

**Decision: defer a shareable Aimtrix decoration schema.** Keep `dev.alucard.aimtrix.profile.v1` as account data visible to this account and its homeserver, not to other Matrix users; account data is not end-to-end encrypted. Do not migrate or copy its bio, banner, sticker references, frame, card, or effect to public profile fields, room state, or messages. The existing Matrix display name and avatar remain the only profile elements Aimtrix deliberately shares through standard profile APIs.

Matrix now permits namespaced custom public profile fields on supporting homeservers, with `m.profile_fields` capability negotiation. That is a plausible future storage path for an explicitly opted-in public bio or banner, but its availability does not make private account data public. A public field can be queried independently of room membership and may be cached by homeservers and clients; deleting the field cannot retract media already fetched or copied. A room-scoped expression would instead need a room event or membership design, whose audience includes room members and possibly federated servers, not a reliable “selected people” ACL. Neither route satisfies a private, revocable selected-room audience today. See the [Matrix profile module](https://spec.matrix.org/latest/client-server-api/#profiles) and [account-data module](https://spec.matrix.org/latest/client-server-api/#client-config).

| Example | Owner sees | Another Aimtrix user sees | Other Matrix client sees |
| --- | --- | --- | --- |
| Private twilight banner and personal bio | Decoration in own editor | Standard display name/avatar only | Standard display name/avatar only |
| No public avatar, or removed avatar | Local default silhouette | Default silhouette after refresh | Its own fallback |
| Custom profile field unsupported or removed | No public decoration control | Standard profile fallback | Standard profile fallback |

Any future public editor must start blank, require a separate explicit publish action with audience and media-visibility language, read back server state, and offer removal with a warning about caches. It must not prefill from private personalization. Remote text and MXC references need strict size/type parsing, authenticated retrieval, data-saver behavior and moderation/block handling. A public MXC is not E2EE, even when uploaded by an encrypted-room user. Proposed namespaced field, **if** implementation is later approved: `dev.alucard.aimtrix.expression.v1`, containing only bounded display values and MXC references. This is a proposal, not a deployed schema. A future implementation needs server capability checks, another-client fallback, deletion/readback, media cache tests, and a separate issue before this decision changes to “approved.”

## Reminders and scheduled sending — reject closed-app promises in the static client

**Decision: reject scheduled message sending and guaranteed timed reminders for the current backend-free release.** An unread reminder is standard `m.marked_unread` room account data, distinct from `m.fully_read` and read receipts; it is not an alarm. Browser timers, service-worker lifetimes and foreground notification APIs cannot guarantee execution after every client is closed. The existing Capacitor `LocalNotifications.schedule` use presents an immediate accepted push; it is not a durable future-message queue. Native alarm APIs could eventually deliver a device-local reminder, but would require permission, reboot/device testing, cancellation and account-isolation work. Native background encrypted sending would also need a proven OS wakeup, device-local credential/crypto lifecycle and membership freshness contract that Aimtrix does not have.

| Mechanism | App closed/offline | E2EE and control | Decision |
| --- | --- | --- | --- |
| Browser timer or service worker | No dependable wakeup or network execution | Keys stay local | Reject as a delivery promise |
| Native local notification | Potential local alert on one device, subject to OS policy | No message send; device-only cancel/edit | Defer behind native acceptance |
| Homeserver or hosted scheduler | Can wake and retry | Plaintext/key custody is unacceptable; pre-encrypted ciphertext has unresolved membership and freshness risks | Reject for Aimtrix's default architecture |
| Standard Matrix `m.marked_unread` | Persists across devices as account data | No clock or delivery deadline | Keep, labeled “mark unread” |

If local timed reminders are reconsidered, store an account-scoped opaque target and UTC instant plus the original IANA time zone for editing; a chosen wall-clock time must resolve ambiguous/missing DST times before saving. Logout must cancel local pending alerts. Edit/cancel must replace a stable reminder ID, with stale callbacks ignored by account generation. A missed alert must display as missed on next app open, never pretend it fired on time. A future server scheduler would need durable idempotency keys, an explicit cancellation acknowledgment, bounded retries, and a proven encrypted send design before any UI claim. No such service or claim is added here. This feasibility direction is based on the actual platform adapters and [push architecture](push-architecture.md).

`npm run proof:scheduling` uses disposable Chromium pages and a synthetic timer/fetch to check that a pending timer dies with its page, reopening a page does not recreate it, offline fetch does not become a retry queue, and New York's 2026 DST transition has a missing and an ambiguous wall-clock time. It also records whether the timer fires while Chromium reports the page frozen or only after resume; the headless lifecycle flag is not an operating-system suspension guarantee. It sends no Matrix event or production request. [PR #206](https://github.com/spencerrung/aimtrix/pull/206) added the proof to CI and closed [#172](https://github.com/spencerrung/aimtrix/issues/172). It does not exercise an Aimtrix scheduler or establish real operating-system suspension, native alarm delivery or provider behavior; those physical-device boundaries remain [#175](https://github.com/spencerrung/aimtrix/issues/175)/[#176](https://github.com/spencerrung/aimtrix/issues/176).

## Matrix-native integrations — operator-managed bots and bridges first

**Decision: select ordinary Matrix room membership as the first integration path; defer an Aimtrix-specific install directory or provider API.** A useful initial workflow is team release alerts: an operator-managed bot posts an `m.room.message` in a chosen room, and users read it in Aimtrix or another Matrix client. Operators can already provision such bots/bridges on the homeserver side; Aimtrix needs no secret in `public/config.json` and no provider-specific browser SDK. This is a supported protocol path, not a claim that Aimtrix ships a release-alert bot.

An administrator installs and configures the bot outside Aimtrix, reviews its Matrix identity and room permissions, then invites or joins it through normal room membership. Members can inspect its sender, mute notifications, leave the room, or remove/ban it with standard power levels. If it stops posting, the room still works; Aimtrix does not invent a false health indicator. Other clients display standard messages and membership. In an encrypted room, the bot is a participant that must implement E2EE and hold its own keys; room members must consent to that trust boundary. A bridge may expose content to another service. No encryption downgrade, plaintext mirror room, token handoff or browser-held integration secret is automatic. Operators should disclose retention and moderation policy before inviting a bot into private rooms. The [Matrix application-service API](https://spec.matrix.org/latest/application-service-api/) requires homeserver-side registration for privileged bridges and cannot be safely represented as a public browser configuration value.

A client-side integration catalog, install flow or webhook composer is **deferred** until a real operator/user demand identifies a provider, the permission and E2EE model is validated, and install/remove/failure acceptance can be tested against disposable infrastructure. Calendar sync, issue tracker commands, and generic webhooks remain ideas, not shipped controls. The default no-integration room remains fully usable.

## Evidence and reconsideration

The decisions follow the current source boundaries (`profilePersonalization.ts`, `MatrixController`, platform notification adapters, and runtime config), synthetic examples above, and linked Matrix specification contracts. No live profile, bot, scheduler, real OS-suspended browser or physical device was exercised. Reconsider each deferred path only with an implementation issue that names the audience/operator, required runtime capability, privacy and E2EE boundary, fallback, and disposable acceptance proof. This decision pass creates no new protocol event and changes no deployed behavior.
