# Delegated Matrix authentication

Aimtrix discovers delegated authentication through the Matrix SDK's `getAuthMetadata()` result. If the homeserver advertises valid OAuth metadata, sign-in uses public dynamic client registration and an authorization-code grant with PKCE. Otherwise the existing Matrix SSO/CAS token flow or password flow remains available according to the server's advertised login methods. The app has no client secret or backend. A provider that refuses public dynamic registration produces a specific unsupported message; Aimtrix does not pretend that a registered client exists.

The browser uses a fragment callback, while native shells use `aimtrix://sso` with a query callback. The generated opaque state, PKCE verifier, device ID, issuer, registered client ID and exact redirect URI are held in tab session storage or the native protected credential store until a single callback consumes them. The callback URL is removed from browser history before storage or network work. State and issuer must match; ambiguous callbacks, provider denial and replay require starting again. The Matrix authorization-code flow used here requests an access token and refresh token, not an OIDC ID token, so an ID-token nonce is not part of this path. The app verifies the resulting Matrix `whoami` device ID before saving credentials and opening the encrypted SDK client.

The SDK refresh hook rotates access and refresh credentials in the platform store before using the new token. A rejected refresh credential becomes a token-free recovery record; a transient provider outage remains retryable. Explicit sign-out tries to revoke the delegated refresh token, then clears local credentials, account databases and private search data. Local cleanup still finishes if the provider is offline. Tokens, verifier, callback code and provider error bodies are absent from test reports and app logs.

Desktop sign-in opens the provider in the system browser through Tauri's opener plugin. Android and iOS use Capacitor App Launcher; the existing deep-link handlers bring the exact callback back to the app. Native callback parsing and secure-store behavior have automated tests, but physical OS/browser handoff, custom-scheme ownership, Keychain/Keystore retention and cold-start callback delivery still require device runs under [#174](https://github.com/spencerrung/aimtrix/issues/174) and [#175](https://github.com/spencerrung/aimtrix/issues/175).

Provider-specific account-management and UIA flows remain a separate interoperability boundary. A homeserver can require reauthentication or an account-management page for password change, device removal, recovery reset or deactivation; this OAuth implementation does not supply a provider-specific UIA stage. A disposable Matrix Authentication Service/Synapse run and a second provider variant are still required before #174 can claim live delegated interoperability. The existing disposable Dex/Synapse test covers **standard Matrix SSO only**.

Relevant local checks: `src/matrix/delegatedAuth.test.ts` covers registration, PKCE, exchange, rotation, revocation, issuer changes and rejected refresh; `src/matrix/MatrixController.session.test.ts` covers callback consumption, cancellation, state mismatch, token-free cleanup and logout; `src/platform/platform.test.ts` covers native callback validation. The full browser and build gates exercise regressions in existing password and standard SSO behavior. Live and physical evidence must be recorded separately from these mocked checks.
