# Delegated Matrix authentication

Aimtrix discovers delegated authentication through the Matrix SDK's `getAuthMetadata()` result. If the homeserver advertises valid OAuth metadata, sign-in uses public dynamic client registration and an authorization-code grant with PKCE. Otherwise the existing Matrix SSO/CAS token flow or password flow remains available according to the server's advertised login methods. The app has no client secret or backend. A provider that refuses public dynamic registration produces a specific unsupported message; Aimtrix does not pretend that a registered client exists.

The browser uses a fragment callback, while native shells use `aimtrix://sso` with a query callback. The generated opaque state, PKCE verifier, device ID, issuer, registered client ID and exact redirect URI are held in tab session storage or the native protected credential store until a single callback consumes them. The callback URL is removed from browser history before storage or network work. State and issuer must match; ambiguous callbacks, provider denial and replay require starting again. The Matrix authorization-code flow used here requests an access token and refresh token, not an OIDC ID token, so an ID-token nonce is not part of this path. The app verifies the resulting Matrix `whoami` device ID before saving credentials and opening the encrypted SDK client.

The SDK refresh hook rotates access and refresh credentials in the platform store before using the new token. A rejected refresh credential becomes a token-free recovery record; a transient provider outage remains retryable. Explicit sign-out tries to revoke the delegated refresh token, then clears local credentials, account databases and private search data. Local cleanup still finishes if the provider is offline. Tokens, verifier, callback code and provider error bodies are absent from test reports and app logs.

Desktop sign-in opens the provider in the system browser through Tauri's opener plugin. Android and iOS use Capacitor App Launcher; the existing deep-link handlers bring the exact callback back to the app. Native callback parsing and secure-store behavior have automated tests, but physical OS/browser handoff, custom-scheme ownership, Keychain/Keystore retention and cold-start callback delivery still require device runs under [#174](https://github.com/spencerrung/aimtrix/issues/174) and [#175](https://github.com/spencerrung/aimtrix/issues/175). The parser rejects repeated `code`, `state`, `error`, or `loginToken` parameters instead of silently choosing the first value. Tauri and Capacitor plugin tests exercise cold-start OAuth URL translation and two-account secure-store persistence across new shell instances; these mock OS plugins and cannot establish real custom-scheme ownership or physical-device handoff.

The [October 3 disposable MAS/Synapse CI run](https://github.com/spencerrung/aimtrix/actions/runs/37153481583) passed seven checks on Linux/x64 Chromium 149: stack startup, static app, disposable account registration, capability discovery, browser login, logout and cleanup. Login verified the Matrix `whoami` identity, saved refresh credential and removal of the callback code; logout verified local removal and rejection of the revoked refresh credential. The report contains only fixed check names and numeric durations. This is live browser evidence for public registration and the first authorization-code session; actual token rotation after expiry was exercised with mocked SDK/provider responses.

The [expanded October 3 MAS/Synapse run](https://github.com/spencerrung/aimtrix/actions/runs/37159797772) passed ten checks. A delegated account created an encrypted room, sent an event, set up recovery and a nonempty server backup, then signed in on a second device. That device saw the old event undecryptable before restoring the recovery key and decrypted it afterward. The run also checked that the latest stored refresh credential is rejected after explicit logout. This is evidence for this disposable MAS configuration; it does not exercise another provider's authorization policy or actual refresh rotation after expiry.

The [RC3 disposable MAS journey](https://github.com/spencerrung/aimtrix/actions/runs/37215237031) forces one `M_UNKNOWN_TOKEN` response on a signed-in device-list read. It requires the SDK to refresh through the real MAS token endpoint, persist different access and refresh credentials, retry successfully, and confirm the new access token with Synapse `whoami`. It then revokes the new refresh credential and requires MAS to reject a direct refresh-token grant. The browser must reach token-free reauthentication: in the recorded RC3 run, revocation led there before the harness needed to inject a second Matrix 401 (`delegatedRevocationAutoReauth: 1`). If a fresh session remains active, the harness injects that 401 as a separate fallback. This proves real rotation, provider rejection, and browser reauthentication on the pinned MAS/Synapse setup, but does not prove natural expiry timing or a rejected near-expiry browser refresh. The report retains only fixed check names and numeric outcomes, never credentials or provider bodies.

The natural-expiry harness adds a separate `delegated-auth-natural-expiry` check. Its disposable MAS 1.26.0 configuration sets `experimental.access_token_ttl: 60`, the minimum documented by that pinned version; production configuration is unchanged. Existing encrypted recovery setup overlaps the token lifetime. After at least 60 seconds from reading the initial session, the original token must receive a real Synapse `401 M_UNKNOWN_TOKEN`, while the unrouted browser must persist different access and refresh credentials and successfully identify itself with the replacement token. The browser then sends an encrypted message, verifies ciphertext on the homeserver and decrypts it again after reload. The expiry/rotation wait shares a 90-second deadline; the separate forced-401/revocation journey remains in place. Reports include only fixed check/category names and numeric elapsed-time/outcome metrics. The [October 6 disposable-stack run](https://github.com/spencerrung/aimtrix/actions/runs/37406251552) passed this natural-expiry check in 59.7 seconds (setup overlaps the token lifetime); it cannot establish another provider's expiry, refresh-grace or revocation policy.

Provider-specific account-management and UIA flows remain a separate interoperability boundary. A homeserver can require reauthentication or an account-management page for password change, device removal, recovery reset or deactivation; this OAuth implementation does not supply a provider-specific UIA stage. A second provider variant and physical native browser handoff are still required before #174 can claim broad delegated compatibility. The existing disposable Dex/Synapse test covers **standard Matrix SSO only**.

For a delegated session, account settings identify password changes and deactivation as provider-managed and hide Aimtrix's Matrix-password forms. Recovery setup/reset can still be attempted without a Matrix password; a provider-specific authorization demand leaves the passphrase in place and explains the trusted-client path. A challenged remote-device sign-out reports that authorization is required. These controls do not assert an account-management URL or provider UIA capability that the homeserver has not supplied.

Relevant local checks: `src/matrix/delegatedAuth.test.ts` covers registration, PKCE, exchange, rotation, revocation, issuer changes and rejected refresh; `src/matrix/MatrixController.session.test.ts` covers callback consumption, cancellation, state mismatch, token-free cleanup and logout; `src/platform/platform.test.ts` covers native callback validation. The full browser and build gates exercise regressions in existing password and standard SSO behavior. Live and physical evidence must be recorded separately from these mocked checks.
