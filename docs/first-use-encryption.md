# First-use encryption confidence

Aimtrix discovers standard Matrix login flows for the selected homeserver before showing password or SSO sign-in. If discovery fails, it explains that availability is unknown. An empty account opens Home with encrypted direct-chat and encrypted-room starting points and a live account-health check. After a direct chat or room is created, its returned room ID opens the new conversation so the first-use path reaches a composer instead of ending at a closed dialog. Recovery settings distinguish new setup from restoring existing secret storage and backup; setup refuses to overwrite either. An existing recovery key is checked against the account's secret-storage key before any cross-signing or backup operation. Recovery reset is a separate, confirmed destructive action using the SDK reset operation. A generated recovery key stays in memory until the user acknowledges saving it; clipboard and download failures keep it visible.

Incoming to-device verification requests are presented with the other user and device identity. The SDK owns request phases and crypto state. Aimtrix offers emoji SAS, QR display, and camera QR scan only when the corresponding Matrix capability and browser camera are available. Starting a QR scan accepts the request before opening the camera, allowing the other client to display its code. The QR reader and generator load only when used. Cancellation and account shutdown detach listeners and stop the camera. The installed Rust SDK processes verified-device secret sharing internally; it does not expose an application approval callback. Aimtrix does not present a pretend secret-approval control. Users can verify a device or restore their existing recovery key instead. Decryption failures use SDK reason codes to distinguish pending, withheld, unverified-device, and historical-backup cases without exposing event contents or keys. The view model checks the failure reason even when the SDK changes the clear event type to a synthetic `m.room.message`, so its diagnostic body never becomes message content.

The browser and mocked tests cover sign-in capability gating, recovery safety, request cancellation, SAS, QR capability gating and ready-before-camera ordering, and decryption guidance. The disposable Synapse journey sets up password-account recovery, waits for a nonempty server backup and secret-storage default key, signs in a fresh device, identifies the exact old encrypted event as loaded but undecryptable, restores with the in-memory key, and requires that same event to decrypt. It also completes incoming emoji SAS between two Aimtrix devices. A later check sends a standard withheld-key to-device event for an old ciphertext to a device without that key and requires actionable guidance. At the end of the run, a confirmed reset replaces the backup, rejects the old recovery key, and accepts the new one. The Dex-backed SSO journey creates an encrypted room and sends an old event before setup. If the server permits setup, a second SSO device must find that exact event undecryptable before restore and decrypt it afterward; if authorization is unsupported, Aimtrix retains the passphrase and directs the user to a trusted client. The optional Element Web journey also checks incoming emoji SAS and scans an Element-generated QR code through Aimtrix's camera decoder with an independently distributed client. The journey and remaining boundaries are described in [the live test guide](live-matrix-tests.md).

Recovery health distinguishes a backup configured on the server from a trusted backup active on this device. Restore checks backup trust and active version before claiming success, and shows fixed progress stages without logging keys. Cross-client QR display in Aimtrix with scanning by another client, independently generated withholding policies and secret gossip, and provider-specific SSO/UIA variants remain open acceptance boundaries for #160 and #161. The live withheld event uses a standards-compliant disposable protocol sender; it does not prove another client's trust policy will produce the same event. Recovery reset deletes previous backup versions and can make old encrypted history unreadable.

The disposable live suite additionally starts from the empty-account guide, checks standard encrypted direct-room creation and `m.direct` state, requires the new conversation to open immediately, and verifies the first message decrypts on the invited peer device. Its outcome is recorded in the CI report; the check does not establish cross-client verification.
