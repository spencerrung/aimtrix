# Exclusive crypto storage ownership

Aimtrix acquires a browser Web Lock for the exact persistent Rust crypto database prefix before creating an authenticated Matrix client. The prefix already identifies the homeserver, Matrix user and device. Different accounts and devices can run concurrently; tabs and installed apps sharing the same origin and browser storage partition share ownership for the same device. The lock name contains only the existing opaque database prefix.

The second window shows **This account is open in another window** without constructing a crypto client, modifying credentials, clearing notification ownership, or removing drafts or keys. **Retry here** attempts immediate acquisition. **Use this window** sends a credential-free BroadcastChannel request asking the owner to hide its workspace and stop. The requester queues for the same Web Lock for up to ten seconds. It never steals the lock or assumes that a missing heartbeat means a suspended owner is dead. If the owner cannot respond, close that window and retry. Without BroadcastChannel, closing the owner and retrying remains available.

Ownership lasts through sync and SDK startup. Shutdown stops the SDK immediately, waits for outstanding initialization/startup and local cleanup, stops any late-created crypto backend, and only then releases the lock. Account switching stops the previous account before acquiring the next device. Browser destruction of a tab releases its Web Locks automatically. A browser without Web Locks refuses encrypted startup and explains the browser/secure-origin requirement; there is no plaintext or in-memory-crypto fallback.

Sign-out and account forgetting acquire every current/retained device lock before invalidating credentials or deleting databases. Dormant removal checks that the vault's device set still matches the locked record. A blocked IndexedDB deletion remains queued in the browser even after error feedback; ownership stays held until those requests actually finish. Retry waits for that cleanup, rather than opening keys while a deletion is pending. The implementation never deletes crypto storage during retry or takeover. Older Aimtrix builds do not honor this lock, so close those windows before upgrading and opening the account in this version.

## Evidence and boundaries

The October 7, 2026 local disposable Synapse run passed installed standalone-PWA refusal in the same Chromium profile, cooperative takeover, bidirectional encrypted send/decrypt, retained historical decryption after reload, abrupt owner-window closure/retry, and cleanup including PWA uninstall and profile deletion. The run used a virtual Linux display and synthetic accounts, with no live account data in its output.

Controller regression tests reproduce concurrent restoration, distinguish devices/accounts, exercise cooperative takeover with delayed shutdown, delayed initialization/startup, unsupported Web Locks, cancellation/timeouts, credential and draft retention, guarded dormant removal and database-cleanup exclusion. Chromium desktop/mobile tests use the real controller, Web Locks and BroadcastChannel with a synthetic SDK client; they exercise simultaneous opens, takeover, owner-window destruction, different accounts, keyboard focus, Axe and short viewports. The production App has a separate ownership-loss/draft-retention test.

Run `xvfb-run -a env AIMTRIX_CRYPTO_HEADFUL=1 node tests/live-matrix/crypto-ownership.mjs` after `npm run build` for a disposable Synapse production-preview journey on Linux. It installs Aimtrix in a temporary Chromium profile, selects standalone mode, launches the real PWA window and checks exclusion beside the signed-in browser window. It also checks encrypted sends before and after same-profile takeover, peer decryption in both directions, retained historical decryption after takeover/reload, another exchange after owner-window destruction, and resource cleanup. Browser lock release after destruction is asynchronous; the harness waits for the browser to report release before retrying. The temporary profile and services are removed; credentials, keys, events and exception bodies are excluded from reports. Output contains only fixed stage names and pass/fail.

The installed-PWA check covers Linux Chromium on a virtual display and the same browser profile. Physical mobile/desktop PWA behavior, native storage partitions, Firefox/WebKit lifecycle behavior and other homeservers remain explicit interoperability boundaries. This work does not close #171's native multiple-account gate. Headless Chromium installs/launches the app but reports browser display mode by default; the standalone acceptance run uses the headful command above.
